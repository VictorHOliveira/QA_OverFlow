Design Patterns para Automação de Testes: A Arquitetura que Sobrevive ao Caos

Victor Oliveira    April 24, 2026 08:35 PM

Por um QA Sênior — 13 anos quebrando coisas de forma organizada

Ao longo de quase uma década e meia construindo e reconstruindo suítes de automação, testemunhei um padrão (sem trocadilho) repetido à exaustão: projetos começam lindos, organizados, promissores. Seis meses depois, são um Frankenstein de código duplicado, lógica de negócio vazando para os testes e manutenção que consome 70% do tempo do time.

O problema raramente é a ferramenta (Cypress, Playwright, Selenium, o que vier amanhã). O problema é arquitetural. E a boa notícia é que os Design Patterns de teste — bem aplicados — são imortais. Eles transcendem linguagens e frameworks porque resolvem problemas humanos de organização, não técnicos de sintaxe.

Vamos ao que interessa: os padrões que realmente entregam valor em 2026, com exemplos práticos e armadilhas fatais.

1. Page Object Model (POM) — Clássico, Mas Nem Todo Mundo Sabe Usar

O POM é o avô dos patterns de automação. Todo mundo conhece, mas poucos aplicam corretamente. O princípio é simples: cada página ou componente da UI é representado por uma classe que expõe apenas ações de alto nível.

Exemplo do que NÃO fazer (anti-pattern visto semanalmente):

# ❌ Mau uso: Page Object virou localizador glorificado
class LoginPage:
         username_input = "#username"
         password_input = "#password"
         login_button = "#login"

def type_username(self, text):
         driver.find_element(self.username_input).send_keys(text)

Isso não é um Page Object, é um repositório de seletores com métodos anêmicos. O verdadeiro POM encapsula comportamento, não elementos.

Exemplo correto:

# ✅ Page Object comportamental
class LoginPage:
    def __init__(self, page):
        self.page = page  # Playwright/Puppeteer/Selenium abstraction

    def login_as(self, user_type):
        """Ação de alto nível que encapsula toda a sequência"""
        if user_type == "standard":
            self._fill_credentials("standard_user", "secret_sauce")
        elif user_type == "locked":
            self._fill_credentials("locked_user", "secret_sauce")

        self.click_login()

        # Já retorna a próxima página
        return InventoryPage(self.page)

    def get_error_message(self):
        return self.page.locator("[data-test='error']").text_content()

    def _fill_credentials(self, username, password):
        self.page.fill("#user-name", username)
        self.page.fill("#password", password)

    def click_login(self):
        self.page.click("#login-button")

A regra de ouro: Um método no Page Object deve retornar outro Page Object (fluxo feliz) ou dados (extração de informação). Nunca expor elementos ou ações cruas.

2. Test Data Factory — O Pattern Mais Subestimado

Aqui está o assassino silencioso da produtividade: testes que dependem de dados hardcoded que existem em um ambiente, mas não em outro. O Data Factory Pattern resolve isso centralizando a criação de entidades de teste.

O problema:

# ❌ Dados espalhados e frágeis
def test_login():
    user = "john.doe@example.com"  # Esse usuário existe no dev?
    password = "Test@123"
    # ...

A solução:

# ✅ Data Factory
class UserFactory:
    @staticmethod
    def standard_user():
        return User(
            email = f"test+{uuid4()}@example.com",  # Dados únicos
            password = "P@ssw0rd!",
            role = "customer",
            payment_method = "credit_card"
        )

    @staticmethod
    def admin_user():
        return User(
            email = f"admin+{uuid4()}@example.com",
            password = "Admin@456",
            role = "admin",
            permissions = ["read", "write", "delete"]
        )

    @staticmethod
    def user_with_expired_subscription():
        user = UserFactory.standard_user()
        user.subscription_end = datetime.now() - timedelta(days=1)
        return user

# Uso no teste
def test_logout():
    user = UserFactory.standard_user()
    api.create_user(user)  # Se necessário criar via API
    login_page.login_as(user)
    # ...

Benefício adicional: As Factories podem ser combinadas com Builders para cenários complexos (veja a seguir).

3. Builder Pattern — Para Cenários de Dados Complexos

Quando sua entidade tem 15+ campos opcionais, o Builder impede a explosão de construtores.

class OrderBuilder:
    def __init__(self):
        self.order = {
            "customer_id": 1,
            "items": [],
            "shipping_address": "Default Address",
            "payment_method": "credit_card",
            "coupon_code": None,
            "gift_wrap": False
        }

    def with_items(self, items):
        self.order["items"] = items
        return self

    def with_coupon(self, code):
        self.order["coupon_code"] = code
        return self

    def with_express_shipping(self):
        self.order["shipping_method"] = "express"
        self.order["shipping_cost"] = 19.90
        return self

    def as_guest(self):
        self.order["customer_id"] = None
        self.order["is_guest"] = True
        return self

    def build(self):
        return self.order

# Uso fluente e legível
order = (OrderBuilder()
         .with_items([product1, product2])
         .with_coupon("BLACKFRIDAY")
         .with_express_shipping()
         .as_guest()
         .build())

Isso torna seus testes auto-documentados. Qualquer QA júnior entende o que está sendo testado.

4. Facade Pattern — Orquestrando Múltiplos Page Objects

Ninguém quer ver um teste com 15 linhas chamando 8 Page Objects diferentes. O Facade esconde a complexidade da orquestração.

class CheckoutFacade:
    """Orquestra o fluxo completo de checkout, escondendo complexidade"""

    def __init__(self, page):
        self.cart = CartPage(page)
        self.checkout = CheckoutPage(page)
        self.payment = PaymentPage(page)
        self.confirmation = ConfirmationPage(page)

    def complete_purchase(self, user, cart_items, payment_info):
        """Um método de alto nível para todo o fluxo"""
        self.cart.add_items(cart_items)
        self.cart.proceed_to_checkout()

        self.checkout.fill_shipping_info(user.address)
        self.checkout.select_shipping_method("standard")

        self.payment.process(payment_info)

        return self.confirmation.get_order_number()

    def complete_purchase_as_guest(self, cart_items, payment_info):
        """Variante do fluxo para usuário não logado"""
        self.cart.add_items(cart_items)
        self.cart.proceed_to_checkout()
        self.checkout.select_guest_checkout()
        # ... resto do fluxo

# Teste limpo e focado em negócio, não em cliques
def test_guest_checkout():
    facade = CheckoutFacade(page)
    order_id = facade.complete_purchase_as_guest([product], credit_card)
    assert order_id is not None

Quando usar: Fluxos de negócio que envolvem múltiplas páginas/steps. Seu teste não precisa saber que existem páginas de carrinho, checkout, pagamento — só precisa saber que é possível finalizar uma compra.

5. Strategy Pattern — Lidando com Múltiplos Locators/Interações

Esse é um dos meus favoritos para projetos que testam a mesma funcionalidade em diferentes contextos (web, mobile, API).

from abc import ABC, abstractmethod

Interface comum

class AuthenticationStrategy(ABC): @abstractmethod def login(self, credentials): pass

@abstractmethod
def logout(self):
    pass

Implementação para Web

class WebAuthStrategy(AuthenticationStrategy): def init(self, page): self.page = page

def login(self, credentials):
    self.page.goto("/login")
    self.page.fill("#email", credentials.email)
    self.page.fill("#password", credentials.password)
    self.page.click("#submit")

def logout(self):
    self.page.click("#user-menu")
    self.page.click("#logout")

# Implementação para API (mais rápido!)
class APIAuthStrategy(AuthenticationStrategy):
    def __init__(self, api_client):
        self.api_client = api_client
        self.token = None

    def login(self, credentials):
        response = self.api_client.post("/auth/login", json={
            "email": credentials.email,
            "password": credentials.password
        })
        self.token = response.json()["token"]
        return self.token

    def logout(self):
        self.api_client.post("/auth/logout", headers={
            "Authorization": f"Bearer {self.token}"
        })

# Teste que pode usar diferentes estratégias
def test_user_profile(auth_strategy: AuthenticationStrategy):
    auth_strategy.login(test_user)
    # ... validações do perfil
    auth_strategy.logout()

# Executa com Web
test_user_profile(WebAuthStrategy(page))

# Mesmo teste com API (mais rápido para Smoke Tests)
test_user_profile(APIAuthStrategy(api_client))

6. Singleton Pattern (Com Moderação) — Para Recursos Caros

Inicialização de browser/contexto é cara. O Singleton garante uma única instância compartilhada.

class DriverManager:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialize()
        return cls._instance

    def _initialize(self):
        # Playwright example
        self.playwright = sync_playwright().start()
        self.browser = self.playwright.chromium.launch(headless=False)
        self.context = self.browser.new_context()

    def get_page(self):
        return self.context.new_page()

    def cleanup(self):
        self.context.close()
        self.browser.close()
        self.playwright.stop()

# Uso em qualquer lugar do projeto
driver = DriverManager()
page = driver.get_page()

Cuidado: Singleton pode esconder problemas de paralelização. Use com contexto isolado (fixtures no Pytest/JUnit resolvem melhor). Prefira injeção de dependência quando possível.

7. Composite Pattern — Validando Componentes Recursivos

Para UIs com estruturas aninhadas (menus, árvores, tabelas complexas).

class UIComponent(ABC):
    @abstractmethod
    def validate(self):
        pass

    @abstractmethod
    def get_children(self):
        pass

class MenuItem(UIComponent):
    def __init__(self, name, locator):
        self.name = name
        self.locator = locator
        self.children = []

    def add_child(self, component):
        self.children.append(component)

    def validate(self):
        assert self.locator.is_visible()
        for child in self.children:
            child.validate()

    def get_children(self):
        return self.children

# Uso: menu com submenus
main_menu = MenuItem("Products", locator_products)
electronics = MenuItem("Electronics", locator_electronics)
phones = MenuItem("Phones", locator_phones)
accessories = MenuItem("Accessories", locator_accessories)

main_menu.add_child(electronics)
electronics.add_child(phones)
electronics.add_child(accessories)

# Valida recursivamente toda a estrutura do menu
main_menu.validate()

8. Repository Pattern — Centralizando Seletores

Para projetos grandes, centralizar seletores evita o caos.

class LoginRepository:
    """Centraliza todos os seletores em um único local"""

    # Usando diferentes estratégias (CSS, XPath, data-attributes)
    USERNAME_INPUT = "input[data-test='username']"
    PASSWORD_INPUT = "input[data-test='password']"
    LOGIN_BUTTON = "input[data-test='login-button']"
    ERROR_MESSAGE = "h3[data-test='error']"

    # Seletores mais complexos podem ter métodos
    @staticmethod
    def get_user_menu_item(user_name):
        return f"div.user-menu:has-text('{user_name}')"

# Uso nos Page Objects
class LoginPage:
    def enter_username(self, username):
        self.page.fill(LoginRepository.USERNAME_INPUT, username)

Vantagem: Quando um dev renomeia data-testid, você altera em UM lugar.

project_tests/
├── config/                 # Configurações por ambiente

Conclusão: Padrões Não São Receita de Bolo

Aprendi da pior maneira: aplicar todos os padrões de uma vez é tão ruim quanto aplicar nenhum. O segredo é evolução incremental.

Comece com POM. Quando sentir dor de dados repetidos, adicione Factory. Quando os testes ficarem muito longos, introduza Facade. Quando múltiplos contextos surgirem, pense em Strategy.

A boa arquitetura não é imposta desde o dia 1 — ela emerge para resolver dores reais do time. E a melhor métrica de sucesso é simples: quanto tempo leva para você adicionar um teste para uma nova funcionalidade? Se a resposta for "minutos", você acertou. Se for "horas ou dias", algo está errado.

Agora vá e organize esse legado. Ou comece certo do zero. Seu eu do futuro (e o onboarding do próximo QA) vão te agradecer. 🧱

— QA Sênior que já refatorou mais código de teste do que gostaria de admitir
